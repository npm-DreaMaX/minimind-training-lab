# 08 从“发现不对”到“知道为什么”：评估与 Debug

训练工程师不只会让命令执行结束，还要能区分：目标预测改善了吗？实际任务完成了吗？异常是数据、算法、数值还是系统造成的？本章把一次诊断展开成证据链。

所有真实事故都有原始记录链接；教学反例会明确标注。允许根因暂时未知，不把合理猜测写成已经解决的问题。

## 1. 先确定你要测哪一种表现

**训练CE**是在不断变化的训练batch上测“给示范token的概率”。**验证CE**在固定留出记录上测同类目标，不反向更新。**自由生成**则让模型用自己已经生成的前文继续回答；它会暴露重复、错误积累、格式不符和不结束等问题。

假设正确答案是“42”，模型给42的概率变高，CE改善；但生成时也许先进入长解释或循环，最后没输出42。反过来，一道题碰巧答对，也不能证明整个验证分布改善。

所以评估至少要记录三件事：用什么样本与目标；模型如何生成；如何给输出打分。只写final loss会丢掉这些条件。

## 2. 怎样保证两个模型的分数可比？

本项目的固定验证协议使用同一512条记录、191,220个有效目标、相同tokenizer、模板、T768和CE口径。官方参考与Hybrid均严格加载相应结构，按同一设备精度协议评估。

| 权重与数据范围 | CE |
|---|---:|
| 官方198M SFT参考，固定512条 | 1.307459 |
| Hybrid最终FP16导出重载，固定512条 | 1.664561 |
| Hybrid训练中的FP32，固定512条 | 1.664181 |
| Hybrid训练中的FP32，完整1066条 | 1.638091 |

前两行可用于这个固定协议下的参考比较。最后一行换了样本范围，不能与第三行相减叫“又提高了0.026”。文件与完整回答见[最终评估证据](../reports/hybrid_final_review_20261006.md)。

这份对照也有边界：官方基座可能已见过本次留出数据，两条分支并非相同从零训练预算，因此它适合分析转换后的表现，不能当作无污染的架构排行榜。

## 3. 读一次生成，哪些字段不能漏？

一次可复核的生成记录应保留checkpoint身份、prompt、实际模板、解码方式、最大新增token、是否出现EOS和完整原文。

`do_sample=False` 的greedy选当前分数最高的token；采样则按分布引入随机性，需要控制seed等。更改temperature、重复惩罚、模板或输出上限，会影响结果，必须另列协议。

`ended_with_eos=false` 且达到token预算，表示被长度上限截停，不代表模型自然说完。短测32token的介绍，不应与允许256token的任务回答直接混比。

本次16题探针有10题严格格式评分、6题定性观察。两个模型的严格格式项都为0/10，不等于“所有知识正确率为0%”：例如要求只输出数字时，多解释也会被判格式不符。应拆开内容、格式、结束与重复问题，保留评分规则和原文。

真实输出中，Hybrid出现过把17+25答成2250、把144÷12答成0，以及要求偶数求和却返回偶数列表。不能为展示删去这些回答，也不能用一题说明所有能力。题目定义见[探针集](../evaluation/text_probes_v1.json)。

## 4. 一个问题怎样变成可检验的假设？

遇到问题，先写清可以被证据推翻的候选解释。比如“模型不行”太泛；“生成cache让位置偏移，导致后续token错误”就可以用同一前缀的cache/full-forward对照检查。

诊断记录按下面顺序写，但不要求每次都长篇大论：

1. 现象：哪个run、step、输入shape、具体异常数值或输出。
2. 初始假设：列出可能原因，并说明什么观察能区分它们。
3. 检查：固定其他条件，一次改变一个关键变量。
4. 证据：命令、config、原始日志及数值。
5. 排除范围：通过这项检查究竟排除了多少，而非无限外推。
6. 根因或未确定：结论要匹配证据。
7. 修复与代价：改了哪些代码/数据/目标，是否改变实验含义。
8. 同条件复验：症状消失，相关数值也正确了吗？
9. 以后识别：什么信号出现时优先检查这里。

下面逐案实践。

## 5. 案例A：loss持续下降，为什么生成仍有问题？

**现象。** 转换后固定CE下降很多，自由回答仍有重复、算术与任务执行错误。单看loss下降无法解释这种差距。

**初始假设。** 可能是cache错；可能是GPU推理数值；可能只因输出太短；可能FP16导出损失精度；也可能是转换损伤、数据与目标不足以在预算内恢复。

**检查与结果。**

| 检查 | 保持什么不变、改变什么 | 观察及解释边界 |
|---|---|---|
| 同前缀 full-forward 对 cache | 同权重、同token，改变推理执行方式 | 第12000步CPU比较最大relative RMS约6.94e-7，argmax一致；减弱该测试范围的cache错误假设 |
| CPU FP32 与 GPU生成 | 对照硬件与数值路径 | CPU也出现问题，不能把全部错误只归给GPU推理 |
| 增大输出预算 | 同prompt，允许更长输出 | 长输出仍错误，不只是短截停 |
| 导出重载验证 | 同固定验证，比较训练态与导出 | CE差约0.00038，不足以解释相对参考约0.357的差距 |
| 官方参考配对 | 同题与协议 | 官方也有错误，但若干任务更贴合要求；不能只展示一边 |

**结论。** 现有检查缩小了一部分实现问题的解释范围，但没有唯一定位剩余差距。它们也没有完整排除GPU训练梯度、数据分布或初始化的问题。

**处理。** 没有把盲加第三轮当作已证实修复。下一步应把“先适应新模块”“改变初始化”“补充适合的训练目标”等拆成独立对照。当前没有启动新训练。

**以后识别。** CE改善但自由生成落后时，同时查看teacher forcing与生成差异、cache、模板、终止条件和迁移过程。原始诊断见[转换恢复分析](../docs/debug/013_hybrid_transfer_recovery.md)。

## 6. 案例B：OOM发生在AdamW，而不是forward

**现象。** Omni资源测试在明确5.3GiB预算、B1T512条件下，forward/backward已执行，但首次建立optimizer状态失败。

**初始假设。** 参数本身过大？激活太多？分配碎片？m/v尚未计入？必须先读traceback定位在哪个操作分配失败，而不是只看最后一行CUDA OOM。

**证据链。** 同条件使用expandable segments后通过，说明分配布局是该测试的重要因素。T1536时allocated本身接近预算，改allocator仍不够；重计算降低激活后通过。再做累积2失败，定位为已有gradient与新激活共存，而不是把首次通过外推为全流程通过。

**修复与验证。** 研究moment暂存CPU，核对状态搬运后的参数/优化器更新一致性；真实模态另做带编码器的检查，不能把T2A结果直接外推给A2A或I2T。

**代价。** 额外RAM、pinned memory和传输；WSL主存很紧，长期运行还需观测swap、验证与保存峰值。没有缩小模型结构，但系统执行方式改变了。

**以后识别。** 先标注forward/backward/optimizer/validation/save哪个阶段；分别记录allocated、reserved、外部占用与状态账本；同样本跨多个更新复验。`empty_cache()`不能释放活跃张量。完整过程见[显存事故](../docs/debug/004_omni_memory.md)。

## 7. 案例C：前向接近，不代表反向接近

**现象。** 把GDN大投影改成BF16的候选，前向输出相对RMS差约0.974%，看似接近；一些衰减门梯度差异却达几十个百分点。

relative RMS定义为 `RMS(candidate-reference)/RMS(reference)`。参考梯度很小时，相对误差会放大，所以同时记录绝对误差和梯度尺度，不能只看一个百分比。

**初始假设。** BF16投影舍入被衰减导数放大；加速核反向差异；被当作真值的FP32参考本身不够可靠。

**诊断转折。** 加入独立逐token递推后发现，默认FP32 FLA路径对某些门的梯度也与独立参考差很多。于是最初“只怪BF16”的判断不充分，必须先修正参考。

**更强证据。** 用FP64自动微分与有限差分检查独立参考，再分别指定Triton IEEE、TF32x3对照。PyTorch的TF32开关并不控制独立Triton所有dot路径。指定精度后，独立参考与完整模型更新/恢复检查支持采用TF32x3。

**仍未采用的部分。** BF16投影候选相对可信参考仍有约7%–9.5%的门梯度差异，超过预先3%的候选界限，因此未进入正式配方。这里的界限是本次预检准则，不是所有模型通用定理。

**代价。** 正式保留较昂贵的FP32线性路径。以数值证据解释代价，不能只说“保险起见所以慢”。原始各轮假设与修正见[精度诊断](../docs/debug/007_hybrid_bf16_gradient.md)。

## 8. 案例D：GPU占着显存，却一直等不到batch

**现象。** 普通MoE资源预检中，worker报 `OSError: [Errno 95] Operation not supported`，训练没有产生step。

**初始假设。** OOM、语料损坏、worker崩溃、进程通信不支持。traceback指向Python multiprocessing的 `socket.bind`，没有指向CUDA分配或分词逻辑。

**判别检查。** 同一段Unix socket绑定在D盘挂载路径失败，在Linux `/tmp` 成功；同份数据的管线检查正常。该证据支持文件系统IPC限制，而不是“模型太大”。

**根因与修复。** TMPDIR被放到Windows DrvFS。将临时IPC目录改到Linux `/tmp/minimind-lab`，项目与数据仍留D盘；增加DataLoader等待超时帮助后续定位。它不改变数学目标。

**复验与识别。** 对应v2预检能够继续执行。以后见“显存占用、无batch、socket.bind错误”，先看临时目录与IPC，不把batch直接降到1掩盖问题。[原始现场](../docs/debug/002_wsl_dataloader_socket.md)

## 9. 案例E：夜里几小时没日志，怎样区分休眠与卡死？

检查PID、最后日志、GPU活动和主机事件。长墙钟间隔可能包含系统睡眠，也可能是数据等待或进程失效，不能只靠最后status=training判定。

本次两段夜间大间隔有Windows睡眠/休眠事件，恢复后的更新计时仍为秒级。旧防睡眠脚本没有正确核查返回值；后来改为同原生线程重复请求并保留心跳。该处理不保证阻止合盖、主动睡眠或电池保护。

重要的是保留判断过程和限制，而不是把所有时间差都算作GPU慢，也不是看到没日志就再启动一个重复训练进程。[事件与修复记录](../docs/debug/015_sleep_pause_and_eta.md)

## 10. NaN和loss spike：没发生过的事故也能练方法

正式Hybrid日志中CE、aux、grad没有记录到非有限事件，不虚构一次“正式NaN已经修好”。真实dLM检查则保留了零监督分母导致NaN的边界反例。

先理解NaN是数值“不再是有效实数结果”的标志。除以0、无有效项的均值、溢出后的非法运算等都可能产生它，单看最终loss不知道最早在哪一层发生。

下面是独立CPU教学反例，不加载正式模型：

```python
import torch
z = torch.zeros(2, 3, requires_grad=True)
y = torch.tensor([-100, -100])
print((y != -100).sum())  # 0：没有一个要评分的目标
print(torch.nn.functional.cross_entropy(z, y, ignore_index=-100))
# 当前验证环境的mean reduction得到nan
```

正确处理应在数据或损失入口明确识别无目标样本/批次，决定过滤还是跳过，并重新核对预算。把NaN替换成0、降低LR或增加显存，都没有说明原来这批到底在学什么。

一般定位顺序是：保留失败样本和最近有效恢复点；检查ID/label范围、有效目标和mask；检查输入、参数、各层激活、loss、梯度第一次非有限的位置；再对照精度、LR和实现。不要先覆写掉现场。

loss spike则先看是否单批难度变化、是否只剩很少标签、grad与路由怎样、固定验证是否持续恶化。偶发高loss与全局数值崩溃需要不同处理。
