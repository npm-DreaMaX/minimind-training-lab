# 09 预训练、SFT、偏好优化、RL、dLM和Omni：它们各在改变什么

学到这里，你已经知道数据、模型、loss、更新和系统怎么连接。本章把这个共同框架用于不同训练阶段。它不是“每种方法我们都训练过”的成果清单：本项目正式完成的是Hybrid转换后的两轮SFT，其余范围在第01章说明。

## 1. 先分开四个问题，再讨论“训练哪种模型”

**结构**决定怎样计算：Full或Linear怎样处理上下文，Dense或MoE怎样处理FFN，视觉/语音编码器怎样接入。**目标**决定奖励什么预测。**数据与预算**决定具体学什么、学多少。**系统**决定怎样在设备上执行。

所以同一个MoE可以做预训练、SFT或偏好优化；同一个SFT目标也能训练Full或Hybrid。dLM则不仅更换注意力可见性，还更换监督对齐和生成过程。把不同概念写成一个名字，不能代替说明它们如何连接。

## 2. AR预训练：从一般文本学习后续token

AR是autoregressive，自回归：后一个token依赖前面的token。预训练可以使用正文，例如“水在常压下加热会……”，让模型沿整段预测后续内容。

数据得到 `[B,T]` 编号，普通非pad位置基本都可作为后续目标。位置t的logits对齐位置t+1，仍是第02、04章的CE与反向传播。

不同于对话SFT，预训练通常不只学习assistant回答。它从大量文本学习语言形式、知识关联与上下文规律。说“预训练”不一定表示随机开始：从已有权重继续学一般文本，也可以叫继续预训练；必须同时说清初始化。

源码看[官方PretrainDataset](../upstream/dataset/lm_dataset.py)与[本项目TokenCorpus](../lab/data.py)。我们的普通198M分支确实从零开始，但在13209步按用户要求停止，不能把它当作完成的基座。

如果loss异常，先检查文本编码、BOS/EOS、shift、pad和重复，再看LR与梯度。预训练loss下降不直接意味着指令遵循好，因为数据未必教过特定的问答格式。

## 3. SFT：在给定问题与上下文下模仿示范回答

SFT把“用户问题＋助手示范”送入模型，只对选定的助手目标计算CE。输入条件不同、监督范围不同，底层依然可以是AR next-token预测。

```text
预训练：一般文本前缀 → 正确的后续文本
SFT：   问题和对话前缀 → 正确的示范回答
```

它不是把每个问题的最终答案单独塞进分类标签，也不是先让模型自由回答再人工给分。训练时使用写好的答案前缀，能够并行计算多个位置。

全参数SFT会更新所有允许训练的参数；只更新部分模块也可以使用SFT目标。“全参数”不表示使用了全部可能数据，也不等于从零。

本次Hybrid就是这种目标，两轮共735,833,934个有效监督token。数据中有长思考、重复和不准确示范；模型提高这些示范的概率，不自动形成更可靠的事实推理。第02章的数据审计和第08章的独立生成必须一起看。

## 4. DPO：同一个问题，为什么一个回答比另一个更值得提高概率？

偏好数据给出同一prompt的两个回答：chosen（更偏好）与rejected（较不偏好）。它不一定是绝对“真/假”，也可能反映风格、帮助程度或标注者选择。

SFT只让模型模仿chosen；DPO使用两者的对比，并与一个冻结参考模型比较。记policy是正在更新的模型，reference是固定参照：

```text
Δpolicy = log Ppolicy(chosen|prompt) - log Ppolicy(rejected|prompt)
Δref    = log Pref(chosen|prompt)    - log Pref(rejected|prompt)
L_DPO   = -log sigmoid(β*(Δpolicy-Δref))
```

序列的log概率由回答有效token的log概率累加。本仓库的[train_dpo.py](../upstream/trainer/train_dpo.py)使用求和，不是按长度平均；prompt和pad的mask也必须正确。

### 4.1 手算一个DPO变化

假设参考对chosen/rejected的log概率为-3/-4，差为1。初始policy差也为1，则相对差为0，loss=`-log(0.5)≈0.6931`。

后来policy的chosen/rejected变为-1/-3，差为2；β取教学值0.1，相对差为1，loss约0.6444。它奖励“相对于参考，更偏向chosen”的变化。

这不是直接预测一个0/1好坏分类标签，也不要求模型把rejected概率变成0。β影响目标尺度和参照约束关系，不能把它看成无关紧要的显示参数。

### 4.2 数据、计算与故障

同批B对回答拼成 `[2B,T]`，policy与reference都计算目标token的log概率；reference不反向，policy反向。通常需要额外参考模型的存储或参考分数缓存，不能拿SFT的显存账本直接照搬。

偏好标签矛盾、chosen总更长、prompt不匹配、回答mask错误，都可能让loss下降却学到不想要的偏好。应记录偏好margin、长度、独立任务表现，并检查标签来源。我们没有本项目DPO训练曲线，不用示意曲线冒充结果。

## 5. RL额外引入了什么：模型自己生成训练样本

强化学习阶段通常由当前策略对prompt生成回答，得到reward，再调整这些生成行为的概率。一次“生成并与环境交互”的过程叫rollout。

与SFT不同，答案不全是固定示范。模型会遇到自己生成的错误前文；奖励可能来自规则、验证器、奖励模型或环境结果。评分本身就是系统的一部分，错误奖励也会引导错误行为。

基本流程：

```text
prompt → 用采样时策略生成回答 → 计算reward
       → 保存回答及生成时的概率
       → 当前模型重算概率 → 构造策略损失 → backward/update
```

这里有三个容易混淆的对象：**当前policy**参与更新；**old policy概率**对应这批回答生成时的策略，用于校正分布变化；**reference**通常是固定模型，用于约束不要偏移太远。old与reference不是同一个概念。

生成时要逐token推进，常常比同长度teacher-forcing训练难以充分并行；再加reference、reward、可能的critic，RL既有算力成本，也有复杂的数据状态和恢复需求。

## 6. GRPO：同题多份回答，用相对表现构造学习信号

GRPO对每个prompt生成G条回答，组内比较reward。当前源码用组均值与总体标准差：

```text
advantage_i = (reward_i - 组均值) / (组标准差 + 0.0001)
```

advantage称优势，表示这份回答相对同题其他回答好多少，不是模型的新权重。

例如reward=`[0,0,1,1]`，均值0.5、标准差0.5，优势约为`[-0.9998,-0.9998,0.9998,0.9998]`。若都得1分，组内相对优势为0，没有这部分偏好方向；KL或aux等其他项仍可能有梯度，不能说整个更新必然为零。

这里reward shape为`[B,G]`，生成目标log-prob通常为`[B*G,R]`，R是回答位置数。prompt、pad以及结束后位置需要正确mask，否则会奖励不属于回答行为的部分。

### 6.1 为什么要有ratio与clip？

设这次生成某个token时概率为0.1，更新后的当前模型给0.2，重要性比值ratio就是2。它描述当前策略相对于采样策略的改变。

GRPO分支采用clipped surrogate。对正优势而言，若clip范围为[0.8,1.2]，ratio从1.2继续增加，不会无限增加同样的裁剪奖励；对负优势，min/max处理要按公式理解，不能一律把ratio夹住后当普通CE。

clip是为了限制某类更新激励，不是把模型参数裁剪到这个区间。它与第04章的梯度范数裁剪不是同一个操作。

### 6.2 当前仓库的奖励实际是什么？

[train_grpo.py](../upstream/trainer/train_grpo.py)里的reward包含长度、think格式、重复惩罚和reward model分数，不能把它说成纯数学正确性奖励。模型可能学会满足格式，却没有真正解决任务。

因此要分别记录各reward分量、组内方差、KL、长度、clip比例、rollout耗时和独立任务表现。总reward上升也可能是“钻评分规则的空子”，必须核对实际输出。

## 7. CISPO与PPO为什么不是同一个选项改个名字？

当前脚本的CISPO分支把ratio上界截断后detach，再乘advantage和当前token log-prob；GRPO分支则使用ratio及其裁剪版本的surrogate比较。梯度流不同，是训练算法改变，不能只说一个更快的开关。

PPO还训练critic，估计某个状态后续能得到多少回报，用以构造优势。仓库[train_ppo.py](../upstream/trainer/train_ppo.py)有value head、returns/advantage计算、policy clip、value loss和KL限制。

可以先把critic理解为“用于估计还可能拿到多少奖励的模型”，而不是事实真伪裁判。critic有参数和optimizer状态，加入它需要新的显存、数值和目标检查。policy reward改善、critic loss降低，也要分别解释。

这一节建立代码入口和概念关系，不代表仅凭几段文字就会独立实现可靠PPO。要深入时，下一步应手工核对一条rollout的每个token：old/current/ref log-prob、reward、advantage、mask和最终loss；本项目尚未完成这个RL实训。

## 8. Agentic RL：工具返回不能当成模型自己生成的动作

Agent轨迹可能是：用户问题 → 模型提出工具调用 → 工具返回 → 模型继续 → 最终答案。不是所有轨迹token都由policy选择。

例如计算器返回“42”，它属于环境观察；如果把它当作模型动作无差别施加策略梯度，就可能优化错对象。需要记录哪些位置来自assistant采样、哪些来自工具插入，以及每轮old log-prob和奖励。

本仓库[train_agent.py](../upstream/trainer/train_agent.py)包含工具调用解析、多轮rollout和模拟工具返回。这里有 `MOCK_RESULTS`，不能把脚本中出现天气/汇率工具名就称为接入了真实外部服务。

验收应检查合法调用、参数、环境返回、回合终止和任务完成；恢复还要考虑rollout轨迹与外部状态。该方向留作后续独立实验，没有在本次Hybrid SFT中暗中完成。

## 9. dLM：把“预测下一个”改为“恢复被遮住的位置”

AR按左到右预测。这个作者实验的dLM使用掩码去噪：把部分可监督token换成mask，让模型根据可见上下文恢复原位置。

教学上可理解为：

```text
原文：这座城市是北京。
带噪输入：这座城市是[MASK]。
目标：在MASK那个位置预测“北京”，可利用右边句号
```

三个关键改变一起发生：可见性从因果改为双向；loss从错位下一token改为同位置重建；生成从逐token追加改成多次填mask。只把 `is_causal=False` 打开，而仍用普通AR的teacher-forcing目标，会造成不合适的目标泄露，不能叫完成dLM改造。

### 9.1 本仓库的真实目标

每条序列抽一个噪声程度t，由它得到mask概率p；在符合SFT监督条件的位置抽样mask，prompt和pad不作为去噪目标。作者使用现有ID27作为mask，并没有为此扩展词表。

```text
loss = sum(实际mask位置的CE / 对应p) / 全部eligible位置数
```

分母不是本次实际mask数。`1/p`补偿抽样概率，但输入条件也随mask变化，不能简单称为普通AR CE的无偏估计。该模型没有单独t embedding，噪声通过输入mask体现，p也进入loss。

[真实CPU检查](../docs/learning/07_ar_and_masked_diffusion.md)使用完整63,912,192参数Dense模型：两条128位置样本，共157个eligible，实际mask87个，手算与模型loss均约9.00501。改变未来token影响dLM早期输出，却不影响AR早期输出，直接验证了可见性区别。

AR与dLM参数形状相同，state_dict严格加载成功，只说明能初始化；它仍需适应去噪目标。作者MoE配置的aux整合也需另审计，不能直接假设与我们的AR CE+aux一致。

### 9.2 生成和恢复有什么不同？

生成先在prompt后放mask，反复forward、按置信度填入候选。位置会重新改变，因此普通AR的旧KV cache不能无论证地跨迭代复用。要测每个输出耗时、迭代数、残留mask与任务表现，不能只比单次forward速度。

真实边界检查发现显式n_valid=0时NaN，以及受控logits偏好mask时最终仍留mask。这些是作者代码边界反例，不是已完成模型的错误率。恢复时还必须重建t与mask采样的RNG。

不能把去噪loss取exp后与AR perplexity直接排名；两者预测条件和目标分布不同。

## 10. Omni：图片、语音怎样成为语言主干可用的输入？

图像和波形不是直接变成普通汉字编号。当前Omni用输入编码器提取特征，再用可训练投影转换到语言主干的768维，并放到相应占位位置。

```text
文字ID → embedding ───────────────────────┐
图像 → 冻结视觉编码器 → 视觉投影 ──────────┼→ Thinker → 文本logits
音频 → Fbank → 冻结语音编码器 → 音频投影 ─┘     ↓ 中间层表示
                                      Talker → 多路音频code logits
```

当前版本训练组合输入是`[B,9,T]`：8路音频code与1路文本；文本输出`[B,T,6400]`，音频为8个`[B,T,2112]`输出。不同模态的编号空间、PAD和STOP不能互换。

Thinker是语言/语义主干，Talker负责音频输出。预计算的音频codes是压缩声音的离散表示，不是每一路都能当作完整语音。具体模型在[sources/minimind-o/model/model_omni.py](../sources/minimind-o/model/model_omni.py)。

### 10.1 不能机械复用AR的数据代码

Omni Dataset已经把输入取`[:-1]`、labels取`[1:]`；模型forward不再shift。我们的AR则由模型内部shift。两段代码拼起来做两次shift，shape可能仍能通过，但学的是错位目标。

音频不同codebook还有相对延迟排列。loss是文本CE，加8路音频CE的平均，再加aux；音频STOP位置加权10倍，分母仍按有效位置计数。把所有模态目标混成一个普通均值，会改变权重。

这些具体定义见[Omni数据与损失](../docs/learning/03_omni_data_and_loss.md)，不能凭“多模态SFT”四个字猜。

### 10.2 冻结参数为什么还可能需要反向？

如果投影位于一个冻结语言主干之前，loss仍需穿过主干，把梯度传回投影。冻结主干参数只表示不更新它们，不表示可以给整段主干套no_grad。

相反，一个冻结输入编码器之前没有要训练的输入模块时，可在合适条件下不保存它的参数梯度路径。应按计算图判断，不能一律把所有冻结部分视为零显存。

真实检查还发现：某些音频增强分支只保留文字，audio projector收不到任务梯度，但AdamW历史与weight decay仍可能让参数变动。所以要同时看输入marker、投影梯度和loss，不能只看参数更新过。

本项目保留了完整315M及真实编码器的短测与OOM过程，正式Omni预算没有完成。它提供系统与接口学习，不冒充完整多模态能力实训。

## 11. 下一次怎样公平比较Full与Hybrid？

先写研究问题，再选对照。

**问题A：同样从零预算，两种架构各学得怎样？** 两边都从各自初始化开始，共享tokenizer、训练/验证划分、数据顺序、长度和有效token预算；明确198M与205M并不完全等参数。固定token预算与固定墙钟预算回答不同问题，应分别报告，不能默认两者同时相等。

**问题B：已有Full模型能否低成本转换？** 共用官方起点；保留原始Full、同预算Full继续SFT、Hybrid转换后SFT；若再比较“先适应新模块”，单独设分支并记录新增预算。

当前完成的是问题B中的一个候选，没有完成匹配Full续训等对照。因此不能从这次结果推出“Hybrid必然差”，也不能反过来保证“从零Hybrid一定更好”。

写实验计划至少包含：假设、唯一主要变化、共享条件、数据指纹、预算、初始化、数值检查、显存/吞吐、固定验证、生成任务、保存恢复与停止条件。多seed可估计随机性；只有一个seed要标明限制。

## 12. 哪些修改是工程优化，哪些改变实验？

提前分词、mmap、无损分片，在token/labels/顺序相同情况下可以是数据管线优化；本项目固定离线增强却与每次随机增强不同，这一部分是recipe改变。

重计算与offload在计算和随机性一致时主要改变执行方式，但需要数值对照。换precision或kernel通常目标形式不变、数值轨迹会变，要检查关键梯度。batch减半accum翻倍要审计分母、aux和尾批。

缩短sequence、改变数据/去重/采样、改变LR/epoch、替换注意力或从AR换dLM，都会改变学习内容、轨迹、结构或目标，必须另记实验含义。不能用“优化”二字省去解释。
