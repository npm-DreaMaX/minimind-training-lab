# 05 显存花在哪里，怎样设计能跑且有意义的 recipe

第 04 章解释了模型、梯度和优化器。现在把它们变成一份存储账本。训练报 OOM 的意思是某次所需设备内存分配失败，并不自动等于“模型参数本身大于显卡容量”。

本章让你能判断：失败发生在哪一段；某个调整释放哪部分内存；代价是什么；它是否改变了训练问题。

## 1. 先分清 GPU 显存、CPU RAM 和磁盘

GPU 显存放设备正在计算的参数、张量等；CPU RAM 放进程、数据加载、CPU 张量和可能卸载的状态；磁盘放语料、日志与 checkpoint。三者不能互相直接加起来作为同一个容量。

我们的 GPU 是 RTX 4060 Laptop 8GB。它还可能承载显示和其他进程，训练不能把标称容量全当作可自由分配空间。正式 Hybrid recipe 还显式设了约 5.3 GiB 的 PyTorch allocator 预算，这是实验约束，不是显卡只有 5.3 GiB。

WSL 能用多少 RAM，还受它自己的限制。历史预检时 WSL 约 7.6 GiB RAM、2 GiB swap；Windows 整机有多少内存，与 Linux 进程当时能用多少不同。硬件变化要重新测，不沿用旧快照当当前值。

## 2. 每个参数不只存一个数

本次正式配置有 P=205,623,072 个独立参数，主要训练状态使用 FP32。FP32 每数 4 字节；1 GiB=1024³ 字节。

| 项目 | 为什么需要 | 理论字节 |
|---|---|---:|
| 参数 | 当前模型函数 | 4P |
| 梯度 | backward 算出的学习信号 | 4P |
| AdamW 一阶 moment | 梯度历史方向 | 4P |
| AdamW 二阶 moment | 梯度平方尺度历史 | 4P |
| 合计 | 假设四类都已建立并驻留 | 16P |

因此基础账本为 `205623072×16/1024³≈3.064 GiB`。这是状态量级估计，不是整次训练峰值。某时刻梯度被清成 None、moments 尚未建立，瞬时数字会低一些。

MoE Top-1 没有把其余专家的参数和状态删除，所以不能简单把此结果除以四。embedding 与 lm_head 共享参数，也不能重复数它们。

## 3. 参数之外，还要保存什么？

forward 中生成的中间表示叫激活。backward 需要其中一些值来应用链式法则，因此不能刚算完就全部扔掉。

对 `[16,768,768]` 的一份 hidden，BF16 约 18 MiB；对 `[16,768,6400]` 的一份 logits，BF16 约 150 MiB、FP32 约 300 MiB。真实 forward 还有投影结果、卷积状态、归一化、路由、专家中间表示、损失临时量等。

“八层×一份 hidden”不是完整激活账本。一层里可能保留多份不同张量，某些函数内部还会转换 dtype 或生成连续副本。分配器缓存、CUDA 上下文和其他进程也占空间。

因此，模型文件约 421MB 并不意味着“训练应该只占几百 MB”。那个文件是 FP16 导出，没带梯度、AdamW、激活或临时缓冲。

## 4. 一次更新的显存怎样随时间变化？

```text
加载参数
  ↓ forward：激活增长
  ↓ backward：梯度出现，部分激活逐渐释放
  ↓ 第一次AdamW：建立m/v，更新临时量增加
  ↓ 清梯度：部分活跃内存下降
  ↓ 下一批：m/v已经常驻，再叠加激活与梯度
```

如果做梯度累积，第二个小批开始时，上一个小批的梯度还在。即使第一批 forward/backward 可以执行，第二批也可能在“已有梯度＋新激活”的峰值失败。

所以显存验证至少要覆盖首次更新和已有 Adam 状态后的更新；只运行一次 forward、甚至只运行第一个完整 step，都不够。

## 5. 三种“显存占用”为何不一样？

| 指标 | 表示什么 | 不能怎样解释 |
|---|---|---|
| `memory_allocated` | PyTorch 活跃张量的设备分配 | 它不是整张卡所有占用 |
| `memory_reserved` | 分配器向设备保留的空间 | 大于 allocated 不等于无条件内存泄漏 |
| `nvidia-smi memory.used` | 驱动看到的设备占用 | 不能全部归给当前模型 |

分配器预留一些空间以复用，避免每次申请都付出高开销。碎片会使“总空闲量看似够”与“能否满足当前分配”不同，但不能见 OOM 就一律归因于碎片。

`empty_cache()` 只能尝试释放未使用的缓存块，不能把仍然活跃、被引用的参数或激活清掉。把它加到每步通常也不是解决容量不足的根本方法。

本项目日志中的 `cuda_peak_allocated` 是**进程启动以来的高水位**，只在启动时 reset，不是本步独立峰值。若要定位阶段，应在专门的 profiling 中同步 GPU、在指定区间重置峰值，然后分段测量；不能悄悄更改正式指标定义。

## 6. activation checkpointing 为什么能省显存？

不使用重计算时，forward 留下较多中间结果，backward 直接用。使用时，只保留一些边界输入，backward 需要时重新执行那段 forward。

```text
普通：forward → 保存内部激活 → backward读取
重算：forward → 少存内部激活 → backward前重做这一段forward
```

它把一部分计算换成显存空间。理想数学目标不变，但需要验证随机性、状态副作用、输出和梯度一致。本项目用非重入 checkpoint，保留 dropout RNG，训练时不允许同时用生成 cache；源码是[lab/checkpointing.py](../lab/checkpointing.py)。

关闭后通常会增加激活占用，可能提速，也可能因需要减小物理 batch 抵消收益。不能没测就承诺“快一倍”。本项目短测 B16 重算约 10.15 样本/s，B2×累积8不重算约 10.52 样本/s，差约 3.7%；物理 batch 也变了，所以这不是只开关重计算的严格消融。[原始效率分析](../docs/debug/014_hybrid_budget_and_efficiency.md)

## 7. BF16、FP32、TF32 各影响什么？

FP32 用 32 位存一个数；BF16 用 16 位，通常减少部分张量存储与计算成本，但有效精度不同。autocast 根据算子选择计算 dtype，不等于把所有参数、梯度和 moment 都变成 BF16。

本次 FP32 主参数、梯度和 moment，外层 BF16 autocast；GDN 内部显式使用 FP32，Triton dot 默认设置为 TF32x3。PyTorch matmul 的 TF32 开关则关闭。这两个软件层的开关不是同一个。

TF32 涉及某些矩阵乘法的内部精度与执行方式，不能理解为“多了一套 19 位模型权重”。我们关心它最终对输出、门梯度和更新有什么影响。

本项目确实遇到“输出接近，门梯度差很多”的候选。后来用独立参考定位数值路径，没有仅凭 loss 有限就采用最快设置。精度候选的证据与诊断在第 08 章。

## 8. batch、seq、accum 和 offload 应该怎样选？

| 调整 | 优先解决哪部分 | 代价与实验含义 |
|---|---|---|
| 减物理 batch B | 同时存在的激活和部分缓冲 | 可能降低 GPU 吞吐；若不补累积，有效 batch 也改变 |
| 增累积 G | 保留每更新样本量 | 不减少参数/moment；需正确 token 加权和跨小批峰值验证 |
| 缩短 T | 激活、注意力及其他长度开销 | 截断更多文本和目标，属于 recipe 改变 |
| 开重计算 | 保存的激活 | 增加重做 forward 的成本，需要一致性检查 |
| 换低精度 | 特定算子的激活和计算 | 有舍入变化，要检查关键梯度 |
| CPU offload | 将部分 GPU 状态移至 RAM | 占主存、PCIe 传输、pinned memory；主机也可能撑不住 |
| 改层数/宽度/专家数 | 模型本体 | 改了研究对象，不能当作纯系统优化 |

单卡有效样本 batch 近似为 B×G，多卡再乘数据并行卡数；有效 token 数还受样本长度和 labels 影响。B4×G4 与 B16×G1 都是 16 条，但还要核对 loss 分母、aux 与最后不满批次，才讨论可比性。

Offload 不是免费扩容。真实 Omni moment 暂存候选每次更新有约 5.04GB 双向传输、额外约 2.35GiB 主存，还要考虑编码器和保存 checkpoint 的峰值。显存通过、RAM 几乎耗尽并持续换页，不适合直接宣布能稳定跑几天。

## 9. 用一个真实 OOM 说明为什么不能只改 batch

Omni 在明确 5.3GiB allocator 预算、B1T512 下，曾在首次建立 AdamW 状态时失败。同条件改用 expandable segments 后通过，支持分配布局影响了这次失败；并不说明所有 OOM 都是碎片。

T1536 时，活跃张量接近预算，改分配器不足，重计算降低激活后通过；累积2又在后续小批失败，因为已有梯度叠加。后来研究 moment 暂存并验证更新一致性，代价是主存与传输。

这是按失败阶段提出假设、单项改变条件、复验得到的链条，而不是试到不报错就结束。原始记录：[Omni 显存诊断](../docs/debug/004_omni_memory.md)。它只证明当时配置的边界，不代表任何 Omni 配方在物理 8GB 上都不行。

## 10. 怎么测速度、估时间，而不误导自己？

throughput 是单位时间处理多少工作。先选口径：样本/s、非 pad 输入 token/s、有效目标 token/s，是不同数字。本项目最常用有效监督 token/s，因为它对应实际 CE 预算。

如果剩余 1 亿有效 token，测得持续 4,000 有效 token/s，那么纯更新估计为 `100000000/4000=25000秒≈6.94小时`。还要另外考虑验证、保存、休眠与数据等待的实际开销。这个例子只是估算方法，不是当前训练 ETA。

短测要跨冷启动和 Adam 状态建立，尽量覆盖真实长度分布。CUDA 异步执行时，CPU 发出命令不等于 GPU 做完，所以计时应在合适边界同步。只拿最快一步外推整轮会过于乐观。

GPU utilization 高表示采样窗口内设备在忙，不保证在高效处理有效目标：它可能在重算、计算 padding 或执行不够高效的 kernel。温度、功耗也要与吞吐一起看；没有持续对应关系，就不能直接声称温控限速。

### 官方“几小时”为什么不能直接当作本次预计时间？

本地锁定的[官方README](../upstream/README.md)训练开销表，针对单卡3090：64M Dense的mini预训练加SFT各一轮约2.31小时；198M普通MoE约3.23小时，并明确标注为经验估算。它不是这台4060 Laptop上的205M Hybrid两轮SFT实测。

比较前要逐项对齐：GPU与功率条件、结构、数据/长度、轮数、有效目标预算、数值路径和重计算。我们的六层GDN有chunk状态计算及对应反向，正式线性路径保留FP32，并使用激活重算；算子与访存模式不同。参数量接近不能推出时间接近。只有同机、同输入、相同计时范围的剖析，才支持把某个开销归因到某个模块。

## 11. 一份可解释 recipe 应该怎样形成？

先统计数据长度和目标覆盖；算基础状态账本；用完整结构检查 forward/backward；测首次与后续 optimizer 峰值；验证数值；比较具有代表性的短测；最后才锁定长训练配置和监测方式。

若修改 T，重新审计被截目标；若改精度，重验关键梯度；若改累积，核对 token 加权；若开 offload，检查 CPU RAM 与更新一致性。每一次调整都对应一个具体问题和可观测证据。
