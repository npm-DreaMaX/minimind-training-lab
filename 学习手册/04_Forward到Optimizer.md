# 04 从一次预测，到参数真的改变

第 03 章的模型最终输出 logits。现在要把“给 token 打分”接到“模型学到了东西”：怎样算 loss，怎样求梯度，谁真正修改参数，为什么还需要 AdamW 的历史状态与学习率调度？

先区分三个动作：**forward 计算预测；backward 计算梯度；optimizer.step 执行参数更新。** 它们不是同一件事。读代码时请沿着这三个动作追踪。

## 1. 用一个参数把整条学习链算完

先暂时不用 6,400 个候选，只设两个候选，正确答案是第 1 个（从 0 数）。输入 x=2，唯一参数 w 初始为 0，模型给出的两个 logits 是 `[0,w*x]`。

这只是数学教学，学习率也为方便手算而设置，不是把我们的 205M 模型换成小模型重新训练。

```text
w=0、x=2
→ logits=[0,0]
→ softmax 后概率=[0.5,0.5]
→ 正确候选概率0.5
→ CE=-ln(0.5)≈0.693147
```

softmax 把分数变成概率，但 CE 不只关心哪个候选排第一。两个模型都猜对时，给正确候选 51% 和 99% 概率的 loss 也不相同。

`ln` 是自然对数。在这里先看三个数就能理解它的作用：正确概率0.1时，`-ln(p)`约2.303；概率0.5时约0.693；概率0.9时约0.105。概率越接近1，惩罚越接近0。这个数不是“答错百分比”，也不能把CE=1理解为全错。

若 w 增加到 0.1，正确候选 logit 变为 0.2，概率约 0.5498，CE 降到约 0.5981。我们想知道：怎样从当前计算自动找到这个有利的调整方向？

## 2. 梯度是什么：参数动一点，loss 怎么动？

一个参数的梯度是 loss 对它的局部变化率。对刚才例子：

```text
正确概率 p = 1 / (1+exp(-w*x))
loss 对 w 的导数 = (p-1)*x
w=0 时，p=0.5，因此梯度=(0.5-1)*2=-1
```

负梯度说明，在这个点附近增大 w 会使 loss 下降。最简单的梯度下降写成 `w_new=w-lr*gradient`，因此减去负数，会把 w 往上调。

梯度不是“正确答案”，也不是当前参数应被直接替换成的值。它只描述局部变化关系，更新大小还取决于优化器、学习率、历史状态和裁剪。

不用相信公式，也能用两次前向近似检查：

```text
gradient ≈ (loss(w+ε)-loss(w-ε)) / (2ε)
```

取 ε=0.000001，实际算得约 -1.00000000003，与解析值 -1 接近。这叫中心有限差分，只适合小规模诊断；205M 每个参数都这样算，代价无法接受。

运行只用标准库的算术演示：

```bash
python -B tools/lesson_examples.py optimizer
```

输出同时给解析梯度、有限差分梯度、更新前后 w 和 loss。演示只改变一个临时标量，不读写正式模型。

## 3. 自动求导怎样走过很多层？

真实模型有许多串联运算。若 `a=w*x`，`p=f(a)`，`L=g(p)`，链式法则是：

```text
dL/dw = (dL/dp) * (dp/da) * (da/dw)
```

PyTorch forward 时记录可求导运算间的依赖，backward 从标量 loss 反向应用这些局部导数，把结果累加到参数的 `.grad`。这就是为什么 forward 的一些中间结果需要留着，也解释了激活显存的用途。

下面是可以在已装 PyTorch 的环境中执行的完整小例子：

```python
import torch

w = torch.tensor(0.0, requires_grad=True)
logits = torch.stack([w * 0, w * 2]).reshape(1, 2)
loss = torch.nn.functional.cross_entropy(logits, torch.tensor([1]))
loss.backward()
print(float(loss.detach()), float(w.detach()), float(w.grad))
# 约 0.693147，0.0，-1.0
```

w 仍是 0，因为这里只有 backward，没有 optimizer.step。这不是出错。若你只检查“grad 存在”，就声称参数已经学过，判断会错。

梯度默认累加。若一个独立更新结束后忘记清理，下次 backward 会加到旧值上，变成意外的跨步累积。本训练器在累积组开始和更新后都用 `zero_grad(set_to_none=True)` 清理。

## 4. 回到真实 Hybrid：loss 的目标和分母

输入 x/y 分别是 `[16,768]`，模型输出 `[16,768,6400]`。源码先去掉 logits 最后一格、labels 第一格，实现当前位置预测下一 token；`-100` 目标不参与 CE。

对 N 个有效目标，本批 CE 为：

```text
CE = 所有有效目标的 -log(正确概率) 相加 / N
```

N 不是 16×768。真实第 1 批 N=7,818；用户头部和 pad 等不直接作为目标。

模型返回 `out.loss`（CE）与 `out.aux_loss`（MoE 辅助损失）。训练器组合后反传。不要误以为 out.loss 已包含 aux，再重复加一遍；也不要漏掉 aux。

验证时这里只汇报 token 加权 CE，模型 eval 模式下 aux 为零。因而训练 `loss=CE+aux` 与验证 CE 不是完全相同的指标，比较时先对齐定义。

## 5. 为什么问题没 label，问题位置仍可能有梯度？

“用户问题不计分”只意味着不要求生成这段问题。但助手回答利用了问题的表示，回答预测错了，loss 可以沿注意力依赖影响处理问题的参数。

已经执行的[完整205M CPU 梯度检查](实操输出/完整Hybrid梯度检查_v2/trace.json)使用真实样本前 128 个位置：

| 观测 | 实测值 | 解释 |
|---|---|---|
| input/logits | `[1,128]` / `[1,128,6400]` | 模型完整，仅观测前缀较短 |
| 有效目标 | 105 | 不是 128 个位置都计分 |
| 模型 CE 与独立重算 CE | 都为 0.53979373 | 标签错位与分母对齐 |
| aux | 0.00567702 | 此次前缀上的路由辅助项 |
| 参数总梯度范数 | 17.93575 | 计算过 backward，没有更新 |
| 无直接监督但有 CE 输入梯度的前缀位置 | 23 个 | 上下文确实参与了答案预测 |

这里特别区分了“CE 单独造成的梯度”和“CE+aux 总梯度”，因为 aux 也可能给输入产生梯度。只看总梯度，不能单独证明是回答依赖带来的。

embedding 与 lm_head 共享参数时，某行权重梯度还可能来自输出候选打分。因此要研究输入位置，应看那个位置的 embedding **输出**梯度，而不是仅看 embedding 权重某行。

这份短前缀的 CE 不能与完整验证 CE 比大小宣称能力提高；样本、长度与计算精度都不同。

## 6. gradient accumulation 怎样省显存？

假设想每处理 16 条记录更新一次，但一次只能装 4 条。可以连续做四次 `forward → backward`，每次释放计算图，把梯度累积到同一份 `.grad`，最后才执行一次 optimizer.step。

```text
小批1 → 梯度加到grad
小批2 → 梯度加到grad
小批3 → 梯度加到grad
小批4 → 梯度加到grad
      → 裁剪 → 更新一次 → 清grad
```

它减少同时驻留的激活，不把模型参数和 AdamW 状态变小，也不需要同时保留四张计算图。

但不能不看分母就把每批 CE 除以四。假设两批分别有 100、900 个有效标签，CE 分别为 2、1：

```text
正确目标均值 = (100*2 + 900*1) / 1000 = 1.1
直接平均批次 = (2+1)/2 = 1.5
```

后一种做法给第一批每个 token 更大权重。本训练器对第 i 批使用 `CE_i*n_i/N + aux_i/G`。N 是累积组有效标签总数，G 是非空小批数；CE 按 token 权重，aux 按小批平均。

本次 Hybrid 的 G=1；停止的普通 MoE 预训练 G=24。即使样本有效 batch 相同，MoE aux 分组、随机性和浮点舍入仍可能让累积与大物理 batch 不完全等价。

## 7. grad norm 和 clip 到底是什么？

把所有参数梯度看成一个很长的向量。它的 L2 范数是各分量平方求和再开方，描述整体梯度尺度。

若梯度是 `[3,4]`，范数是 5。设裁剪阈值为 1，就把整组梯度按同一比例缩成 `[0.6,0.8]`，方向保持，范数变成 1。实际实现有小稳定项，数值可能略小于理论值。

本训练器记录的是**裁剪前范数**。首步 45.8114，大于阈值 1，不意味着裁剪失效。应去看 `clip_grad_norm_` 的返回值定义和它位于 optimizer.step 之前的位置。

裁剪抑制一次更新中异常大的梯度，但不是所有不收敛的治疗方法。错误标签、错误目标或错误梯度符号，裁小后仍是错误信号。

## 8. AdamW 为什么不等于“参数减去学习率乘梯度”？

AdamW 为每个参数维护一阶历史 m 和二阶历史 v，还保存已更新次数 t：

```text
m = β1*m + (1-β1)*g
v = β2*v + (1-β2)*g²
m_hat = m / (1-β1^t)
v_hat = v / (1-β2^t)
w_new = w*(1-lr*weight_decay) - lr*m_hat/(sqrt(v_hat)+eps)
```

m 记忆梯度方向，v 记忆平方尺度。偏差校正补偿从零历史开始时的缩小效应。weight decay 单独按比例收缩参数，称解耦权重衰减。

回到 w=0、g=-1 的教学例，用 β1=0.9、β2=0.999、lr=0.1：第一次 m=-0.1、v=0.001，校正后约为 -1、1，更新后 w≈0.1，CE 降到约 0.598139。这些数已在演示脚本中实际核对。

正式 Hybrid 的峰值 lr 是 1e-5，不是教学例的 0.1；默认 eps=1e-8、weight_decay=0.01。本训练器将所有可训练参数放入同一优化器组，没有另外排除 norm 的衰减。

m/v 在首次 optimizer.step 时建立，造成额外显存需求。这解释了为什么“forward 和 backward 都成功了”，仍可能在第一次更新时 OOM。

还有一个易错点：`grad=None` 和数值全为 0 的梯度不同。PyTorch AdamW 跳过 grad=None 的参数；有零梯度时仍可能受历史 moment 和 weight decay 影响。不能把“参数变化了”单独当作它收到有效任务信号的证明；Omni 的真实案例见[模态与梯度说明](../docs/learning/03_omni_data_and_loss.md)。

## 9. scheduler 怎样决定每一步的学习率？

学习率是更新尺度。太大可能损坏已学表示，太小可能在预算内学得不足；不能脱离初始化、batch、数据和目标给出一个万能值。

本次没有 warmup，使用 cosine 从 1e-5 降到接近 1e-6。设 s 是更新前已完成步数，S=113082：

```text
lr(s) = 1e-5 * [0.1 + 0.45*(1+cos(pi*s/S))]
```

s=0 时使用 1e-5；s=S/2 时为 5.5e-6；接近末尾时接近 1e-6。第一条日志写 step=1，使用的是更新前 s=0 的 LR，不是错了一步。

Warmup 是先从较小 LR 逐渐升上来，本实验配置为 0，不要把别的训练惯例写成我们实际用了。改变总预算 S，也会改变原来中间步骤的 cosine 值，因此 resume 时不能悄悄修改 epochs。

## 10. 把真实训练循环读成一段完整逻辑

打开[lab/train.py](../lab/train.py)，从 `for x,y,n in batches` 向前后追踪。实际顺序：

1. DataLoader 提供本组数据，计算各批有效目标数及总数。
2. 根据更新前 step 设置 LR，清掉旧梯度。
3. 把输入/标签送 GPU，在外层 BF16 autocast 下 forward。
4. 按有效 token 权重组合 CE 与 aux，检查有限值，然后 backward。
5. 所有小批完成后裁剪梯度，执行 AdamW step，再清梯度。
6. 同步 CUDA，更新 step、cursor 和 token 计数，写日志。
7. 在约定间隔评估、保存；这些开销不在前面的单步计时里。

源码中没有的机制，不凭惯例补写进去。例如这次 BF16 路径没有使用 FP16 GradScaler；GDN 内部又显式关闭 autocast 用 FP32，不能把整个模型叫成“全 BF16 训练”。

## 11. 不更新、梯度异常和 loss 不下降时怎么查？

先找它发生在链条的哪一步：有效目标是否为零；loss 是否有限；目标参数 `requires_grad` 是否为 true；是否被 detach/no_grad 切断；梯度是否存在且非零；step 是否执行；LR 是否为零；参数变化是否只是 weight decay；固定验证是否真的停滞。

单步 loss 比前一步大，可能只是换了更难的 batch。`backward` 后参数不变可能是正常的只读梯度检查。盲目加 epoch 或改 LR 前，先回答这些问题。
