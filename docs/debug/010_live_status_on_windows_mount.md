# Windows 挂载盘状态文件短暂缺失

## 现象与影响

等待第5001步的 `runs/preflight_window_v6_scheduler/` 在读取正式训练的 `status.json` 时收到 `FileNotFoundError` 并退出。正式训练PID453590仍持续更新；未发生训练OOM、checkpoint丢失或梯度中断。该故障会使后续预检不再自动触发，不能因主训练正常就忽略。

## 假设与证据

最初需要区分目录被删除、路径拼错、训练进程退出，以及状态发布瞬间的文件系统行为。故障后的原路径存在且步数继续增加，原始异常指向与主训练一致的路径，因此排除持久路径错误和主进程退出。训练器通过写临时文件再 `Path.replace()` 发布状态，不能仅凭“原子替换”的编程意图断言所有挂载层的并发读都无间隙。

`tools/probe_status_publication.py` 在独立临时目录执行2000次替换，不接触训练文件：

| 位置 | 读取次数 | 短暂不存在 | JSON损坏 | 写入失败 |
|---|---:|---:|---:|---:|
| 项目所在 `/mnt/d` | 2553 | 293 | 0 | 0 |
| Linux `/tmp` | 19285 | 0 | 0 | 0 |

原始结果及实际执行源码在 `reports/status_publication_probe_v1/`。这证明此环境的Windows挂载路径能够复现该读取窗口；它没有定位到WSL/Windows内部某一实现函数，也不能证明所有WSL版本都有相同行为。两处运行时长不同，因此次数不应当作严格的跨文件系统性能比较。

## 修复与验证

增加 `lab/live_status.py`：只对短暂不存在和JSON未完整可读重试，默认最多30秒；第一次失败与恢复均记日志，持续失败明确抛出异常。其他I/O异常直接保留。尚未启动的未来阶段允许返回不存在，已经观察到状态的阶段则使用有界重试。

四个协调脚本使用该读取方法。没有改动训练的forward、loss、backward、优化器或状态发布代码。正式训练PID未重启，只替换了尚未启动子任务的两个等待进程，并重新排队失败的预检调度器。旧日志和调度器失败目录保留；实际替换命令、PID及源码在 `runs/coordinator_repair_v1/`。

`tools/validate_live_status.py` 检查短暂缺失后恢复、损坏JSON后恢复、永久缺失超时、未来阶段尚不存在，以及D盘2000次并发替换。2473次成功读取、最终step1999，全部通过。记录在 `reports/live_status_reader_validation_v1/`；这是针对本次真实故障的回归验证。

修复后的协调器记录：`runs/preflight_window_v6b_scheduler/`保留原排期，随后由v6c提前执行；v6c与v7b均已结束并自动恢复主训练。持续等待完整阶段的协调器为 `runs/completed_language_evaluation_v2/`、`logs/language_pipeline_orchestrator_v2.log`。

## 以后如何识别与限制

先看主训练PID、metrics最后时间和step是否继续推进，再区分训练失败与监控/调度失败。单次读取失败不等于训练停止；反过来，主训练正常也不意味着未来阶段一定有人接续。遇到连续30秒不可读仍需调查，不能无限吞掉异常或把旧状态冒充实时状态。

本修复保证读取容错，不承诺机器断电后的持久性。checkpoint使用临时文件再替换，恢复仍检查文件、配置、源码指纹、优化器、RNG和数据cursor；这次没有实施断电注入，不能将JSON读取测试称为checkpoint断电安全证明。

## 相邻检查：未持锁的进程不能清空持有者PID

检查调度器如何取得主训练PID时，发现 `lab/train.py` 原先先以 `open('w')` 打开锁文件再 `flock`。这仍能阻止双重GPU训练，但第二个被拒绝的进程会提前截断文件，使调度器失去正确PID。它不是上述已发生异常的根因；当前未观察到它影响正式运行。

在独立临时目录对训练源码抽取的真实锁定片段进行双进程复现：原版本第二进程被拒绝后PID文本为空；改用 `a+` 并在成功持锁后才truncate/write，第二进程仍被拒绝、原PID完整保留。结果和执行片段在 `reports/gpu_lock_pid_regression_v1/`。此修复仅影响下次进程启动的锁管理，现有训练继续运行，下次正常恢复会保存新源码快照。
